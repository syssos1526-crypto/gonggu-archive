# ZEN-A — 데이터 포트폴리오 케이스 스터디

> 이 문서는 ZEN-A를 "데이터 수집·분석이 가능한 서비스 구조"로 고도화하는 첫 단계를
> 설명합니다. 지금 시점에는 개발자 본인만 사용하는 단일 사용자 환경이며, 여기서
> 다루는 내용은 **실제 사용자 행동에 대한 일반화된 분석 결과가 아니라, 그런 분석을
> 가능하게 만드는 데이터 구조와 설계 근거**입니다.

## 1. 서비스 문제 정의

뷰티/패션 인플루언서 공동구매(공구)는 여러 SNS·채널에 흩어져 있어 소비자가
"지금 어떤 공구가 열려 있는지, 언제 마감되는지, 믿을 만한 인플루언서인지"를
한 곳에서 파악하기 어렵다. ZEN-A는 공구 정보를 검색·카테고리·인플루언서
신뢰도 기준으로 한 곳에 모아 보여주고, 사용자가 관심 있는 상품/인플루언서를
저장해 마감을 놓치지 않도록 돕는 서비스다.

## 2. 기존 핵심 기능

- 홈: 진행중/최근 등록/인기 브랜드 섹션으로 공구 노출
- 검색: 공구/상품/인플루언서 탭, 공구진행순·관심순 정렬
- 카테고리 필터: 뷰티(스킨케어·클렌징 포함), 패션, 리빙, 식품/건강
- 공구 상세: 가격 비교, 마감 정보, 외부 구매 링크, 관련 공구 이력
- 인플루언서 상세: 프로필, 신뢰도, 진행 공구 목록
- 이메일 회원가입/로그인/로그아웃, 이메일 인증
- 관심(하트) 등록·해제: 상품/인플루언서 단위, `/mypage`에서 목록 확인
- `/feed`: 관심 등록한 상품/인플루언서와 연결된, 아직 끝나지 않은 공구를
  마감 상태별로 모아 보여주는 관심 기반 피드

## 3. 데이터 모델 및 이벤트 설계

기존 테이블(`users`, `products`, `influencers`, `group_buys`, `interests`)은
그대로 두고, 신규 `event_logs` 테이블 하나만 추가한다(`scripts/add-event-logs.sql`).

| 컬럼 | 설명 |
|---|---|
| `id` | 이벤트 고유 id |
| `user_id` | 이벤트를 발생시킨 사용자(로그인 사용자만 기록) |
| `event_type` | 이벤트 종류 (아래 표) |
| `group_buy_id` | 관련 공구(nullable) |
| `product_id` | 관련 상품(nullable) |
| `influencer_id` | 관련 인플루언서(nullable) |
| `metadata` | 이벤트별 부가 정보(jsonb, nullable) |
| `created_at` | 발생 시각 |

수집하는 이벤트 5종:

| event_type | 발생 시점 | metadata / 연결 컬럼 |
|---|---|---|
| `search_submitted` | 검색 결과 페이지 조회 시 | `metadata.query`, `metadata.result_count` |
| `interest_added` | 상품/인플루언서 하트 등록 | `product_id` 또는 `influencer_id` |
| `interest_removed` | 하트 해제 | `product_id` 또는 `influencer_id` |
| `group_buy_viewed` | 공구 상세 페이지 조회(로그인 사용자) | `group_buy_id`, `product_id`, `influencer_id` |
| `purchase_link_clicked` | 외부 구매 링크 클릭 | `/go/[groupBuyId]` 내부 리다이렉트에서 기록 후 실제 구매처로 이동 |

로깅은 모두 **최선형(best-effort)**으로 구현했다(`lib/analytics/logEvent.ts`).
`event_logs` insert가 실패해도 예외를 던지지 않고 콘솔 로그만 남기며, 기존
검색/관심/상세조회/구매링크 기능은 그대로 동작한다.

`purchase_link_clicked`는 기존처럼 상세 페이지의 "구매하러 가기" 버튼이 바로
외부 URL로 나가는 대신, 신규 내부 라우트 `app/go/[groupBuyId]/route.ts`를
거치도록 바꿨다. 이 라우트는 서버에서 `group_buys.purchase_url`을 직접 조회해
그 값으로만 리다이렉트하므로(클라이언트가 목적지 URL을 지정할 수 없음),
오픈 리다이렉트 위험 없이 클릭을 기록한 뒤 기존과 동일하게 구매처로 이동한다.

## 4. 측정하려는 핵심 가설 3개

1. **관심 등록이 실제 구매 행동(구매 링크 클릭)으로 이어지는가** —
   `interest_added` 이후 같은 상품/공구에 대한 `purchase_link_clicked`가
   비관심 상품 대비 더 높은 비율로 발생하는지.
2. **마감 임박이 관심 등록·구매 링크 클릭을 늘리는가** — 마감까지 남은
   기간에 따라 `interest_added`/`purchase_link_clicked` 빈도가 달라지는지
   (`scripts/analytics-queries.sql`의 4번 쿼리로 근사 확인).
3. **검색이 실제 탐색·전환으로 얼마나 이어지는가** — `search_submitted`의
   `result_count`가 낮은 검색어일수록 이후 `group_buy_viewed`/
   `purchase_link_clicked`로 이어지는 비율이 낮아지는지.

## 5. 현재 추천(피드)은 ML이 아닌 baseline

`/feed`는 사용자가 직접 등록한 관심 상품/인플루언서를 기준으로 아직 끝나지
않은 공구를 모아 보여주는 **규칙 기반 baseline**이다. 행동 로그나 협업
필터링을 사용하는 추천 모델이 아니며, 이번 단계에서 추가한 `event_logs`는
향후 이 baseline을 데이터 기반으로 평가·개선하기 위한 수집 인프라다.

## 6. 한계

- 현재는 개발자 본인 계정으로만 로그가 쌓이는 **초기 로그 수집 단계**다.
- 사용자 1명의 행동 패턴을 일반 사용자 행동으로 일반화할 수 없다.
- 공구 데이터 자체도 아직 소량(수작업으로 추가한 실제 공구 몇 건 + 데모
  데이터)이라, 통계적으로 유의미한 분석에는 표본이 부족하다.
- `scripts/analytics-queries.sql`의 결과는 "쿼리가 의도대로 동작하는지"
  검증하는 용도이며, 실제 인사이트로 보고할 단계는 아니다.
