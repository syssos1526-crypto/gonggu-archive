# ZEN-A — 데이터 포트폴리오 케이스 스터디

> 이 문서는 ZEN-A를 "데이터 수집·분석이 가능한 서비스 구조"로 고도화하는 과정을
> 설명한다. 지금은 개발자 본인과 동의한 소수 테스트 사용자(지인)만 실제로 로그를
> 남기는 초기 단계이며, 여기서 다루는 내용은 **일반화된 사용자 행동 분석 결과나
> 추천 성능 주장이 아니라, 그런 분석을 가능하게 만드는 데이터 구조와 설계
> 근거**다.

## 1. 서비스 문제 정의

뷰티/패션 인플루언서 공동구매(공구)는 여러 SNS·채널에 흩어져 있어 소비자가
"지금 어떤 공구가 열려 있는지, 언제 마감되는지, 믿을 만한 인플루언서인지"를
한 곳에서 파악하기 어렵다. ZEN-A는 공구 정보를 검색·카테고리·인플루언서
신뢰도 기준으로 한 곳에 모아 보여주고, 사용자가 관심 있는 상품·인플루언서를
저장해 마감을 놓치지 않도록 돕는 서비스다. 타깃 사용자는 여러 인플루언서를
동시에 팔로우하며 공구 소식을 놓치고 싶지 않은 뷰티·패션 소비자다.

## 2. 핵심 기능

### 사용자 기능

- 홈: 오늘 마감 임박 히어로, 오늘 종료/진행 중/오픈 예정/최근 종료 공구를
  날짜 기준 상태 계산 헬퍼로 명확히 분리해 노출(상태 뒤섞임 없음)
- 검색: 공구/상품/인플루언서 탭, 공구진행순·관심순 정렬
- 카테고리 필터: 뷰티(스킨케어·클렌징 포함)/패션/리빙/식품/건강
- 공구 상세: 가격 비교, 마감 정보, 외부 구매 링크(내부 리다이렉트 경유),
  관련 공구 이력
- 인플루언서 상세: 프로필, 신뢰도, 진행 공구 목록
- 이메일 회원가입/로그인/로그아웃, 이메일 인증
- 관심(하트) 등록·해제: 상품/인플루언서 단위, `/mypage`에서 목록 확인
- `/feed`: 관심 등록한 상품·인플루언서와 연결된, 아직 끝나지 않은 공구를
  마감 상태별로 모아 보여주는 관심 기반 피드

### 관리자 데이터 관리 기능 (`/admin`)

일반 사용자는 접근할 수 없는 관리자 전용 도구로, 서비스 운영에 필요한 실제
공구 데이터를 관리자가 직접 등록·관리할 수 있게 한다.

- 공구 등록: 기존 상품/인플루언서 검색 선택 또는 신규 등록을 한 화면에서
  처리, 상품 이미지는 URL 입력 또는 로컬 파일 업로드(Supabase Storage)
- 공구 관리: 목록·검색, 일정(시작/종료일·가격·구매 링크·게시물 링크) 수정
- 상품 관리: 목록·검색, 상품명·브랜드·카테고리·메인 이미지 수정
- 분석 대시보드: 5절 참고

## 3. 아키텍처

- **Next.js 16(App Router) + React 19**: 서버 컴포넌트 중심 렌더링, 모든 쓰기
  작업은 Server Actions로 처리. 클라이언트 자바스크립트는 관리자 폼의 검색/파일
  업로드 등 실제로 상호작용이 필요한 곳에만 최소로 사용한다.
- **Supabase**:
  - Auth — 이메일 회원가입·로그인·이메일 인증, `@supabase/ssr`로 서버 세션 관리
  - Postgres — `products`/`influencers`/`group_buys`/`users`/`interests`/`event_logs`
  - Storage — 관리자 상품 이미지 업로드 전용 버킷(`product-images`)
  - Row Level Security — 모든 테이블에 적용, 역할별 최소 권한 원칙(7절)
- **Vercel**: 배포·자동 빌드. 프로덕션 도메인을 기준으로 Open Graph 이미지 등
  절대 URL을 생성한다.

서버 컴포넌트에서는 목적에 따라 세 종류의 Supabase 클라이언트를 구분해 쓴다:
로그인 여부와 무관한 공개 조회는 anon 싱글턴, 로그인한 사용자 본인 데이터
(찜 여부·이벤트 기록)는 세션 쿠키 기반 클라이언트, 관리자 쓰기 작업과 분석
집계는 관리자 검증을 통과한 뒤에만 쓰는 service-role 클라이언트.

## 4. 데이터 모델 및 이벤트 설계

기존 테이블(`users`, `products`, `influencers`, `group_buys`, `interests`)에
`event_logs` 테이블을 추가했다(`scripts/add-event-logs.sql`).

| 컬럼 | 설명 |
|---|---|
| `id` | 이벤트 고유 id |
| `user_id` | 이벤트를 발생시킨 사용자(로그인 사용자만 기록) |
| `event_type` | 이벤트 종류 (아래 표) |
| `group_buy_id` | 관련 공구(nullable) |
| `product_id` | 관련 상품(nullable) |
| `influencer_id` | 관련 인플루언서(nullable) |
| `metadata` | 이벤트별 부가 정보(jsonb, nullable) |
| `created_at` | 발생 시각 |

수집하는 이벤트 5종:

| event_type | 발생 시점 | metadata / 연결 컬럼 |
|---|---|---|
| `search_submitted` | 검색 결과 페이지 조회 시 | `metadata.query`, `metadata.result_count` |
| `interest_added` | 상품/인플루언서 하트 등록 | `product_id` 또는 `influencer_id` |
| `interest_removed` | 하트 해제 | `product_id` 또는 `influencer_id` |
| `group_buy_viewed` | 공구 상세 페이지 조회(로그인 사용자) | `group_buy_id`, `product_id`, `influencer_id` |
| `purchase_link_clicked` | 외부 구매 링크 클릭 | `/go/[groupBuyId]` 내부 리다이렉트에서 기록 후 실제 구매처로 이동 |

로깅은 모두 **최선형(best-effort)**으로 구현했다(`lib/analytics/logEvent.ts`).
`event_logs` insert가 실패해도 예외를 던지지 않고 콘솔 로그만 남기며, 기존
검색/관심/상세조회/구매링크 기능은 그대로 동작한다.

`purchase_link_clicked`는 기존처럼 상세 페이지의 "구매하러 가기" 버튼이 바로
외부 URL로 나가는 대신, 신규 내부 라우트 `app/go/[groupBuyId]/route.ts`를
거치도록 바꿨다. 이 라우트는 서버에서 `group_buys.purchase_url`을 직접 조회해
그 값으로만 리다이렉트하므로(클라이언트가 목적지 URL을 지정할 수 없음),
오픈 리다이렉트 위험 없이 클릭을 기록한 뒤 기존과 동일하게 구매처로 이동한다.

## 5. 관리자 분석 대시보드 지표 정의 (`/admin/analytics`)

PostgREST가 SQL의 `GROUP BY`/집계 함수를 직접 지원하지 않아, 아래 지표는
원시 이벤트 행을 조회한 뒤 서버(`lib/queries/analytics.ts`)에서 직접 집계한다.
대응하는 읽기 전용 SQL 원본은 `scripts/analytics-queries.sql`에 있다.

| 지표 | 정의 |
|---|---|
| 최근 7일 이벤트 유형별 수 | `created_at`이 최근 7일 이내인 로그를 `event_type`별로 카운트, 내림차순 정렬 |
| 많이 검색한 검색어 | `search_submitted` 로그를 `metadata.query`로 그룹화해 검색 횟수 집계, `metadata.result_count`의 평균도 함께 계산 |
| 공구별 참여도 | 공구별 `group_buy_viewed`/`purchase_link_clicked` 건수와, 같은 상품에 대한 `interest_added` 건수(상품의 공구 이력이 여러 건이면 각 공구에 동일하게 반영되는 근사치) |
| 인플루언서별 참여도 | 인플루언서별 `group_buy_viewed`/`purchase_link_clicked` 건수 |

이벤트 유형명은 화면에 사람이 읽기 쉬운 한국어 라벨(검색/관심 등록/관심 해제/
공구 상세 조회/구매 링크 클릭)로 표시하고, 로그가 0건인 지표는 에러 대신
자연스러운 빈 상태 문구를 보여준다. 화면 최상단에는 "현재는 초기 테스트
사용자 로그 수집 단계이며, 사용자 행동을 일반화한 분석 결과가 아닙니다"라는
문구를 항상 고정 표시한다.

## 6. 측정하려는 핵심 가설 3개

1. **관심 등록이 실제 구매 행동(구매 링크 클릭)으로 이어지는가** —
   `interest_added` 이후 같은 상품/공구에 대한 `purchase_link_clicked`가
   비관심 상품 대비 더 높은 비율로 발생하는지.
2. **마감 임박이 관심 등록·구매 링크 클릭을 늘리는가** — 마감까지 남은
   기간에 따라 `interest_added`/`purchase_link_clicked` 빈도가 달라지는지.
3. **검색이 실제 탐색·전환으로 얼마나 이어지는가** — `search_submitted`의
   `result_count`가 낮은 검색어일수록 이후 `group_buy_viewed`/
   `purchase_link_clicked`로 이어지는 비율이 낮아지는지.

## 7. 현재 추천(피드)은 ML이 아닌 baseline

`/feed`는 사용자가 직접 등록한 관심 상품/인플루언서를 기준으로 아직 끝나지
않은 공구를 모아 보여주는 **규칙 기반 baseline**이다. 행동 로그나 협업
필터링을 사용하는 추천 모델이 아니며, `event_logs`는 향후 이 baseline을
데이터 기반으로 평가·개선하기 위한 수집 인프라다.

## 8. 보안

- **Row Level Security**: 모든 테이블에 RLS를 적용했다. 특히 `interests`와
  `event_logs`는 "본인 행만" 조회·기록할 수 있도록 정책이 걸려 있으며, 관리자
  기능을 추가하는 동안에도 이 정책들을 완화한 적이 없다.
- **관리자 서버 검증**(`lib/auth/admin.ts`의 `requireAdminUser()`): 서버 전용
  환경변수 `ADMIN_USER_ID`와 로그인 사용자의 실제 id를 비교해, 일치하지 않으면
  404를 반환한다(관리자 화면 존재 자체를 드러내지 않음). `/admin` 하위 모든
  페이지와 모든 관리자 서버 액션·조회 함수가 각자 이 검증을 다시 수행하며,
  상위 레이아웃 검증에만 의존하지 않는다.
- **secret key(service-role)의 서버 전용 사용**: 관리자 쓰기 작업(상품/
  인플루언서/공구 생성·수정, Storage 업로드)과 분석 대시보드의 전체 로그 집계
  에만 `SUPABASE_SECRET_KEY`를 사용하며, `requireAdminUser()` 통과 이후에만
  호출된다. 이 키는 클라이언트 코드에 노출되지 않고, 일반 `authenticated`/
  `anon` 역할에는 이 기능들을 위한 새 권한을 부여하지 않았다 — 필요한 최소
  권한만 담은 개별 SQL 파일(`scripts/grant-service-role-*.sql`)로 분리해
  관리자가 직접 실행하도록 했다.

## 9. 한계

- 지금은 개발자 본인과 동의한 소수 테스트 사용자(지인)만 실제로 로그를 남기는
  **초기 로그 수집 단계**다. 사용자 규모가 작아 어떤 지표도 일반 사용자 행동을
  대표한다고 볼 수 없다.
- 공구 데이터 자체도 아직 소량(수작업으로 추가한 실제 공구 몇 건 + 데모
  데이터)이라, 통계적으로 유의미한 분석에는 표본이 부족하다.
- `/admin/analytics`의 집계 결과는 "데이터 파이프라인이 의도대로 동작하는지"
  확인하는 용도이며, 실제 서비스 인사이트나 추천 성능 개선 효과를 주장하는
  단계가 아니다.
